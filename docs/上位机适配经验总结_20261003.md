# 外置驱动器上位机适配经验总结（2026-10-03）

记录把旧版《电机模组串口上位机 V1.03》改造成 **MicroDriver V2.10 上位机 V2.11**
这一轮工作的结论与踩坑。目的不是复述改动，而是让下一次协议变更少走弯路。

---

## 0. 起点与终点

| 项目 | 旧版 V1.03 | 本版 V2.11 |
|---|---|---|
| 依据协议 | 电机模组串口通讯协议 V1.2 | 外置驱动器通讯协议 V1.4（2026-10-03 修订） |
| 串口 | 921600，可选 | `460800 8N1`，无校验无流控 |
| Node ID | 1~31 可改 | 固定 `1`（编译期常量） |
| MID | 默认大端，可切换 | 固定小端 |
| 位置量纲 | 无符号 | `int16` 有符号，1 LSB = 65 count |
| 清错 | 写 `0x6040=0x0080` | `0xF1 0x12` |
| 服务/参数 | 堵转电流/时间、波特率 | `0xF1 0x10~0x15`、`0x2020` 安全配置、`0x2021` 安全状态 |
| 扩展遥测 | 无 | `0x2010` 三相电流、`0x2015` 编码器累计 |

结果：95 项自动测试 + GUI 冒烟全通过，代码与文档已推送到 `Rotation-Model`。

## 1. 最重要的一条：应答方向必须以固件源码为准

### 现象

上位机读 DID 全部超时，界面报 `read_did 失败`。

### 排查与根因

旧上位机（V1.2 时代）的流程是：

```text
写 0x601 服务请求 → sleep 6 ms → 发 0x581 查询 → 读应答尾
```

而当前固件 `App/Src/protocol.c` 里：

```c
/* proto_handle_svc() */
case SID_READ_DID:
    r = proto_did_read(did, sub, &value, &bytes);
    if (0 == r) {
        proto_build_svc_response(out, SRID_READ_OK, did, sub, value, bytes);
        proto_send(MSGID_SVCRSP_BASE + BOARD_PROTO_NODE_ID, out, SVC_DLEN);  /* 主动下发 */
```

固件的 MID 分发只认 `0x601 / 0x181 / 0x281 / 0x201 / 0x200 / 0x600`，
**`0x580+NID` 不是可查询报文**，主机发过去只会被记成 `rx_unknown_mid`。

于是实际发生的是：

1. 6 ms 等待太短（USB-RS485 转换器的 latency timer 常见 16 ms），应答还没到；
2. 转身去发 `0x581` 查询，固件不理；
3. `_query()` 发请求前会清输入缓冲，把**刚刚到达的正确应答一起清掉**；
4. 三次重试全部超时 → `read_did 失败`。

### 结论

- 协议文档只写"从机应答"，**没有写应答由谁发起**。这类方向性问题必须回源码确认。
- 改造老上位机时，它原有的时序假设可能绑定的是老固件行为，不能整段照搬。
- 超时值要覆盖链路固有延迟（USB-串口 latency timer 常见 16 ms），
  不能按"460800 下一帧只要 0.3 ms"的线速直觉取 6 ms。
- 修法：服务流程改为**接收固件主动下发的应答尾**，等待窗口 200 ms，超时才重发请求；
  发请求前的清缓冲只放在请求之前，不会吃掉本次应答。

## 2. 从机应答没有 Header/MID，只能靠"预期 DLEN + CRC"重同步

从机应答是 `DLEN + Data + CRC`，不带 `0xAA` 和 MID。一旦字节流错位，
无法靠帧头切分，只能：

1. 在滚动窗口里只挑**等于预期 DLEN 的字节**作为候选起点；
2. 长度够就按 `AA + Response_MID + DLEN + Data` 算 CRC；
3. CRC 不过就右移一字节继续找；
4. 单次询问最多发 1 次 + 自动重试 2 次。

预期 DLEN：Status1 = `5`，Status2 = `3`，服务应答 = `8`。

**启动窗口里的 `0x84` 不是"固件发了非法 DLEN"**，而是接收流错位产生的噪声字节。
上位机不应该把它当协议错误弹窗，而应该丢弃并重同步，把丢弃字节数记到日志里。

配套做法：连接后先做启动握手，连续拿到 **2 轮**完整合法的 Status1+Status2
（或最多等 3 s）再进入周期轮询，避开适配器上电建立期的垃圾字节。

## 3. 控制帧超时：主机侧新出现的"隐性义务"

V1.4 修订版给使能状态加了看门狗：使能后超过 `0x2020/03`（默认 **200 ms**）
没有收到合法 Control1 / `0xF1` 帧，从机会：

1. 标记通讯失联（`0x2021/02` bit4）；
2. 执行正常受控停车；
3. 停车后下使能。

对界面的影响很直接：**"发一帧使能然后不管"必然在 200 ms 后自动停车**。

上位机的处理：

- 使能时会说明该约束并询问是否自动开启 20 ms 周期发送；
- 控制页常显当前超时值（连接后从 `0x2020/03` 回读）；
- 安全状态面板能直接看到"通讯失联保护已触发"。

固件细节（源码确认，别想当然）：看门狗在 `s_ctrl_enabled == 0` 或停车过程中
直接 `return`，而首次对齐期间 `s_ctrl_enabled` 还是 0，所以
**"使能 → 对齐 1.2 s → 开始跑"不会被超时打断**，真正计时是从进入控制环开始。

## 4. 量纲与符号：最容易埋雷的一类改动

- V1.2 的变更历史曾把位置改成 `0~65535`，但正文一直写有符号；V1.4 明确按正文实现。
- 老上位机按无符号 `struct.unpack("<Hbb")` 解析 → 负目标会变成大正数，方向完全反掉。
- 做法：在 DID 目录里给每条显式标注 `signed` 与 `bits`，统一走一个
  `decode_did_value()`，不要在各处手写格式串。
- 版本号是 **BCD**：`0x00021003` → `V2.10.3`、`0x00010400` → `V1.4.0`。
  按位移当整数显示会得到 `V2.16.3` 这种错值。

---

## 5. 模拟器必须复刻固件行为，否则测试越多越"自信地错"

最初为了省事，模拟器把服务应答放进"待查询"缓冲，正好复刻了上面那个错误假设。
结果是 **73 项测试全绿**，但一连实机就 `read_did 失败`。

把模拟器改成"收到请求立刻主动下发应答"之后，才和固件一致；
随后新增的停车/看门狗/安全 DID 测试才真正有意义。

结论：模拟器是"人对协议理解的编码"，理解错了它也跟着错。
**关键时序行为必须拿固件源码或实机抓包交叉验证**，测试通过不能替代这一步。

## 6. 回归测试最划算的锚点：文档里的字节级示例帧

把协议正文里每个示例帧都写成逐字节断言（含 CRC），例如：

```text
AA 01 02 05 80 0A 00 00 14 4A    位置使能，目标 10 LSB，Iq 20%
AA 01 06 08 F1 12 01 00 00 00 00 00 44    清错
05 80 0A 00 00 14 93              Status1 应答尾
```

好处：协议一改，示例帧先变，测试立刻红，比人眼 diff 文档可靠得多。
本次遇到的 CRC 口径、MID 字节序、DLEN、有符号位置，都能被这类断言覆盖。

## 7. 协议升级建议固化为固定流程

1. 新版协议文档先与上一版做 diff（`git diff --no-index`），列出新增/变更条目；
2. 逐条回固件源码确认实现口径：常量、返回码、边界、生效时机、生效条件；
3. 更新协议层（帧/CRC/服务/DID 目录），补字节级测试；
4. 把模拟器改到同一口径；
5. 更新界面（新服务按钮、新参数、新状态、新的操作约束）；
6. 更新 README 与测试用例文档，把协议原文同步进仓库；
7. 全量测试 + GUI 冒烟，再提交推送。

## 8. 工程与协作上踩过的坑

| 坑 | 表现 | 处理 |
|---|---|---|
| 换行符污染 diff | 1400 行的 `app.py` 全篇标红 | 工作区是 CRLF、库内是 LF；用 `git diff --ignore-cr-at-eol` 看真实改动（实际只有 3 个文件几行） |
| 动到别人的工作副本 | 旧仓库有未提交改动 | 用临时克隆 + 正常提交推送，不覆盖对方工作区；未提交内容先 `git stash` 留备份 |
| 本地代理 | git 报 `Failed to connect ... over proxy 127.0.0.1` | `~/.gitconfig` 给 github.com 配了 `127.0.0.1:7890`；Clash 未开时用 `-c http.https://github.com.proxy=` 临时绕过 |
| git 所有权校验 | `dubious ownership` 拒绝操作 | 跨用户目录用 `-c safe.directory=*` |
| 真实 Python 环境 | 沙箱内无法创建/运行 | venv 与 GUI 冒烟需要提权执行 |

## 9. V1.4 修订版新增条目（已实现）

| 项目 | 位置 | 上位机处理 |
|---|---|---|
| 正常停车 | `0xF1 0x13` | 控制页按钮，先减速再下使能 |
| 快速停车 | `0xF1 0x14` | 控制页按钮，立即断开 |
| 急停并锁存 | `0xF1 0x15` | 二次确认；锁存期间使能返回 `0xE5`，需 `0xF1 0x12` 清错 |
| 控制帧超时 | `0x2020/03` 默认 200 ms | 使能时提示并可选自动开 20 ms 周期；超时值常显 |
| 位置软限位 | `0x2020/01`、`0x2020/02` | 参数页可读写，做上下限交叉校验，仅停机可写 |
| 安全状态 | `0x2021/01~0x0D` | 安全状态面板，含状态机/标志/版本/故障快照 |

## 10. 尚未闭环的风险

1. `0x2021/02` bit4（通讯失联）、bit6（急停锁存）只在模拟器验证过，需实机复测；
2. 控制帧超时对"周期发送间隔抖动"的容忍度需实测（20 ms 周期 vs 200 ms 超时余量很大，
   但 USB 拥塞时的抖动仍应观察）；
3. 位置/速度的带载验收、18000 rpm 的温升与长期运行尚未覆盖；
4. 1 号板 RS485 发送链路的硬件一致性问题仍在，与软件无关但会表现为偶发重同步。

---

## 11. 一句话结论

**协议文档定义"应该是什么"，固件源码定义"实际是什么"，实机日志定义"真的是什么"。
三者对不上时，先查源码，再改模拟器，最后才动界面 —— 顺序反了就会像这次的
`read_did 失败` 一样，测试全绿但一连线就卡死。**
